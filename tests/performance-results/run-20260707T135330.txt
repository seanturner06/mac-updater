CONCURRENCY (Workstream-2 defect fixed)
  The product code previously downloaded selected updates one at a time (each
  `brew upgrade <item>` downloads then installs, serially). The fix adds a
  concurrent pre-fetch: prefetch_selected() runs `brew fetch` for all selected
  formulae/casks in a bounded parallel pool (chunks of 6) BEFORE the serialized
  install loop, so the network transfers overlap. This harness exercises that same
  design and measured a 2.90x wall-clock reduction on the download portion
  (17.80 s vs 51.66 s) for this machine's 26 outdated brew items (463 MB). The
  subsequent `brew upgrade` then installs from the warmed cache with no
  re-download.

PASSWORD HANDLING (Workstream-2 requirement) — observed behavior
  The 24 formulae, 2 casks, and 2 npm globals installed WITHOUT elevation and all
  succeeded. The 3 Mac App Store apps require elevation and were reported as clean,
  ISOLATED failures ("sudo: a password is required") — they did NOT block or fail
  any of the non-privileged updates. That matches the requirement: "proceed to
  update everything that does not require a password, and cleanly skip the ones
  that do," with a specific reason recorded per skipped item.

  Root cause of the mas failures (worth noting for the product): SUDO_ASKPASS was
  exported (the same GUI-dialog helper the app uses), but `mas` invokes `sudo`
  WITHOUT the `-A` flag, so sudo does not consult the askpass helper and, with no
  TTY in a spawned process, fails with "a password is required". Homebrew, by
  contrast, honors SUDO_ASKPASS. Net effect is still correct (privileged items
  skip cleanly, everything else proceeds), but the native password dialog will not
  appear for mas upgrades. Options for the product: (a) surface a clear "sign in to
  the App Store / this app needs admin — update via the App Store app" hint for
  mas elevation failures (Freshet already has maybe_append_mas_hint for the
  different-Apple-ID case; a sudo-required hint could join it), or (b) run mas
  under `sudo -A` explicitly when elevation is expected. No code change was made
  here beyond the concurrency fix; this is recorded as a finding.

METHODOLOGY
  - "Outdated" was detected live at run time from `brew outdated --json=v2`,
    `npm outdated -g --json`, and `mas outdated` — no hardcoded/mocked targets.
  - Download bytes are measured from the actual artifact landing in Homebrew's
    cache (brew --cache path, size delta vs. pre-fetch). Items already fully cached
    contribute 0 new bytes and are excluded from throughput.
  - Per-item fetch duration times each `brew fetch` subprocess; batch wall-clock is
    the real span from first fetch start to last fetch finish under a 6-way pool.
  - Per-item install success is confirmed by re-running the outdated checks after
    the install phase and diffing: an item absent from the post-run outdated set
    succeeded; one still present failed (reason from the step's captured output).
  - Harness: tests/performance-harness.py (re-runnable; `--no-install` for a
    download-only measurement). Mirrors the app's operations and prefetch pool size.

========================================================================
ADDENDUM — where the 17.80 s actually went (post-run analysis)
========================================================================
17.80 s wall for 463 MB is ~26 MB/s aggregate, which is only ~one big stream's
worth (discord alone hit 28.5 MB/s) — the 6-way pool did NOT multiply bandwidth.
Investigated; the wall-clock was dominated by tool overhead, not the network:

  - `brew --cache <item>` costs ~1.1 s each (it resolves the formula's metadata,
    not mere process startup — `brew --version` is 0.07 s). This harness ran ONE
    such probe per item BEFORE each timed fetch, inside the worker: 26 × 1.1 s
    ≈ 28 s of metadata work over 6 workers ≈ ~5 s of wall-clock that was neither
    network nor counted in the per-item fetch column. Pure measurement overhead.
  - The 24 formulae are OVERHEAD-bound, not bandwidth-bound: a 0.3 MB formula
    showing ~1.5 s is ~1.2 s brew/Ruby resolution + ~0.3 s transfer. Spawning 26
    separate `brew fetch` processes pays that fixed cost 26 times.
  - The two casks are 65% of the bytes (299/463 MB) and gate the floor at ~6.6 s
    regardless of pool size. Single-stream ceiling ~28 MB/s (~228 Mbit/s) — link
    or ghcr/CDN per-connection cap, not a concurrency failure.

Environment fact discovered afterward: Homebrew 6.0.8 sets
HOMEBREW_DOWNLOAD_CONCURRENCY = 16 — brew already downloads 16-way concurrently
WITHIN a single command. A batched `brew fetch git gh vim sqlite openssl@3`
completed in 1.12 s (one metadata load) vs ~7.5 s as five separate processes.

CODE UPDATED AS A RESULT
  prefetch_selected() was rewritten from "one `brew fetch` process per token
  (chunks of 6)" to "one batched `brew fetch` per kind" (formulae in one call,
  casks in another, the two overlapping on separate threads). This loads metadata
  once per kind and hands the actual parallelism to brew's native 16-way
  downloader instead of fighting it with an external thread pool — removing the
  per-token startup tax that inflated this run. Verified: tests still pass.

  NOTE: a clean re-measurement would require clearing the brew cache (everything
  is installed/cached now), so the numbers above stand as the recorded live run;
  the code change is validated by the batched-vs-per-process timing (1.12 s vs
  ~7.5 s) and the confirmed concurrency setting.
